# P115 cloud adapter

## Public operations

`P115CloudAdapter` implements the `Cloud115Adapter` port:

- The installed synchronous `p115client` transport leaves an additional 200 ms
  idle interval after one API request finishes before the next begins. This
  spaces calls made during paging and reconciliation; it does not replace the
  account-level cooldown after a rejected request or prove that a persistent
  `RemoteRateLimited` classification is a temporary quota response.

- `submit` accepts a standard `magnet:?xt=urn:btih:<infohash>` URI, normalizes
  the infohash, and calls `clouddownload_task_add_url(..., type="ssp")` with
  the verified target directory identity. Only a successful, schema-valid
  receipt containing the exact requested normalized hash is accepted; a stable
  task ID may accompany it. A task ID alone or HTTP success is not a receipt.
- `iter_tasks`, `list_tasks`, and `find_task` reconcile a bounded task ledger;
  infohash matching is normalized and case-insensitive.
- `fs_files`, `list_files`, `get_file`, `mkdir`, and `move_file` operate on
  verified directory/file identities. New production organization does not
  require a rename API.

This reference records the `Cloud115Adapter` port contract and local fixture
coverage only. No real-device verification or installed `p115client` package
or version compatibility is established by this repository.

## Inventory proof

Task pages request the configured page size and stop only on an empty page,
explicit completion, a proven total, or a short page relative to the requested
size. A page cap, malformed envelope, failed envelope, contradictory total, or
missing task API raises `RemoteInventoryIncomplete`; it never proves absence or
authorizes a second submit.

A timeout, malformed receipt, failed or contradictory envelope, or receipt
whose identity does not match the requested infohash leaves submission status
unknown and moves the episode to `needs_review` with `download_pending` as its
resume status. Reconcile using a complete task inventory and exact normalized
infohash before any later decision. Unknown is not absence: stop without
automatically resubmitting, and do not turn an ambiguous response into a
successful `submitted` transition.

Recursive file inventory uses explicit file/directory metadata and IDs, not a
filename suffix. Depth, directory, and file caps are fail-closed. Directory
paths are resolved from the account-root identity chain through complete
listings; a configured path is never passed as an ID. Root ID/path mismatch,
ambiguous names, incomplete listings, or missing explicit identity block writes.

## Organization safety

The organizer persists the target path before any remote write. For new 115
selections it places the original filename in a per-file child directory under
`Season N`, records the returned directory ID before moving, verifies a
complete empty directory listing, then moves the selected remote file by ID.
Recovery compares the persisted directory ID and file ID, size, and available
fingerprint. It never calls ordinary rename. An existing different file or
ambiguous directory opens a conflict review rather than being accepted.

The child directory is a path namespace, while its remote directory ID is the
identity used for recovery. This prevents collisions with previously organized
episodes under the pipeline's own serial runner. The installed 115 API has no
documented server-side exclusion against an unrelated writer that discovers
and writes to the same new directory concurrently; deployment validation must
keep that namespace dedicated to the pipeline.

Relevant executable coverage is in `test_p115.py` and `test_organizer.py`,
including page-2/page-cap behavior, root proof, identity listings, and
no-replace conflicts.
